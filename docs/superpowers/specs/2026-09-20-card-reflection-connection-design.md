# 오늘의 카드: 반응과 연결

상태: 사용자 승인 후 두 피처 브랜치에 구현. 로컬 실행 및 검증 범위는 `docs/card-reflection-local-check.md` 참고.

## 목적과 범위

기존 카드를 다시 읽고 현재의 반응을 남긴 다음, 원할 때 다른 책의 카드와 연결한다. 반응 저장만으로 경험을 완료할 수 있다. 연결이나 덱 생성은 필수가 아니다.

검토 대상 저장소:
- 프론트: `/Users/kmw/Projects/readingDeck/readingdeck-front`
- 백엔드: `/Users/kmw/Projects/readingDeck/readingdeck-back`

## 확인한 기존 구조

- 홈의 `DailyStackSection`은 복습 카드 클릭 시 상세로 이동하고 `PATCH /cards/:cardId/revisit`을 호출한다. 자동 넘김은 5초 간격이다.
- Card에는 마지막 재방문 시각과 횟수만 있다. 반응의 이력은 없다.
- 카드 상세는 페이지와 모달이 `CardDetailView`를 공유한다.
- 백엔드는 NestJS, TypeORM, PostgreSQL이며 migration을 사용한다. 추가 확인: 앱은 비운영 환경에서 자동 스키마 동기화도 켠다.
- CardEmbeddingService에는 개인 카드 의미 검색이 이미 있다. 현재 검색은 입력 텍스트 임베딩을 생성하며, 다른 책 필터는 없다. 카드 생성·수정 시 임베딩 동기화 실패를 허용하므로 임베딩 누락을 정상적으로 처리해야 한다.
- 덱 생성은 노드와 연결선을 함께 저장할 수 있다. 연결선에는 type과 label이 있다.
- 기존 그래프 수정은 모든 노드·연결선을 삭제 후 재생성한다. 간단한 연결 추가용으로 전체 그래프를 조회·수정·덮어쓰지 않는다.

## 접근 방식

1. 반응만 먼저 출시: 가장 작지만 책 사이 연결이라는 가치를 검증할 수 없다.
2. 반응 + 선택적 연결 + 기존 의미 검색 재사용: 권장. 기존 자산으로 전체 경험을 검증한다.
3. 자동 덱 생성과 AI 해석까지 포함: 분류 정확도와 운영 부담이 커지므로 이번 범위에서 제외한다.

## 사용자 흐름

1. 홈에서 오늘의 카드를 읽고 `지금의 생각 남기기`로 카드 상세에 진입한다. 카드 자동 넘김은 제거한다.
2. 상세 본문 아래에서 `지금 이 생각은 어떤가요?`에 답한다.
   - `여전히 동의해요` → agree
   - `생각이 달라졌어요` → changed
   - `실천해 봤어요` → tried
   - `더 생각해 볼래요` → pondering
3. 반응 하나와 선택 메모(최대 500자)를 명시적인 저장 버튼으로 저장한다. 선택만으로 저장하지 않는다.
4. 저장 성공 뒤 `오늘의 생각을 남겼어요`와 `다른 카드와 연결하기`를 보여준다. 바로 종료해도 완료다.
5. 연결을 선택하면 다른 책의 후보 최대 3개와 `직접 찾기`를 제공한다. 후보를 고르지 않아도 된다.
6. 카드 선택 후 관계를 선택한다: `비슷해요`, `반대돼요`, `이어져요`, `질문이 생겨요`.
7. 저장할 내 비공개 그래프 초안 덱을 선택하거나 새 덱을 만든다. 신규 덱 이름은 `오늘 이어진 생각`으로 채우고 수정 가능하게 한다.
8. 명시적인 연결 저장 후 덱 보기 링크를 제공한다. 다음 연결에서는 마지막 저장 덱이 유효한 경우 기본 선택하고 사용자가 바꿀 수 있게 한다.

반응은 개인 이력으로만 보관한다. 덱에 반응 메모를 자동 복사하지 않으며, 공유 덱에 개인 반응이 노출되지 않는다. 카드 상세에 날짜·반응·메모를 최신순으로 보여주고 각 항목 삭제를 지원한다. 편집은 이번 범위에서 제외한다.

카드가 한 장뿐이어도 반응은 가능하다. 다른 책 카드가 없으면 `다른 책에도 카드를 남기면 연결할 수 있어요`를 표시한다. 같은 책 카드만 있을 때 억지로 후보를 표시하지 않는다.

## 반응 데이터와 API 제안

새 `card_reflection` 테이블: id, cardId(FK, 카드 삭제 시 CASCADE), reaction, note(nullable), requestId(UUID), createdAt. 원래 card.thought를 덮어쓰지 않는다. 소유권은 card → book → user로 검증한다.

- `POST /cards/:cardId/reflections`: reaction, note?, requestId. 같은 요청 재전송은 같은 결과를 반환한다. DB에서 (cardId, requestId) 유일성을 보장한다.
- `GET /cards/:cardId/reflections`: 최신순 20개, cursor 기반 더 보기.
- `DELETE /cards/:cardId/reflections/:reflectionId`: 소유권 검증 후 삭제.

반응 저장과 기존 revisit 횟수는 별개다. 기존 방문 동작은 유지하고 반응 저장에서 재방문 횟수를 다시 증가시키지 않는다. 최초 버전의 이력은 반응 시점만 남기며 원본 카드 편집 전 본문 전체를 버전 보관하지 않는다.

## 관련 카드 선택

`GET /cards/:cardId/related`를 추가한다. 원본 소유권을 검증한 뒤 저장된 원본 임베딩과 같은 사용자의 다른 책 카드 임베딩을 비교한다. 개인·다른 책 필터는 후보 수 제한 전에 적용한다. 요청마다 새로운 임베딩을 생성하지 않는다.

결과는 연결의 정답이 아닌 후보로 표시한다. 임베딩이 없거나 후보가 없으면 빈 목록을 반환한다. 실패해도 반응 저장과 직접 선택은 작동해야 한다.

직접 찾기는 기존 내 책 목록 → 해당 책 카드 목록 API를 재사용한다. 원본 책은 제외한다. 전체 카드 검색 시스템을 새로 만들지 않는다. 최종 저장에서도 두 카드 소유권과 서로 다른 책 여부를 재검증한다.

## 연결 저장

- 새 덱: 기존 `POST /decks`로 두 노드와 관계선을 함께 생성한다. status=draft, mode=graph로 고정한다. 응답 유실 재시도에 대비해 선택적 requestId와 사용자별 유일성을 추가한다.
- 기존 덱: `POST /decks/:deckId/card-connections`로 fromCardId, toCardId, relation을 받는다. 그래프 전체를 교체하지 않고 필요한 노드·연결만 추가하고 preview를 갱신한다.
- 관계는 기존 연결의 type/label에 저장한다. 새 전역 카드 관계 테이블은 만들지 않는다. 연결 수명은 덱에 종속된다.
- 기존 덱은 비공개 graph 초안만 선택 가능하며 서버도 검증한다. 연결 추가로 발행이나 공개 공유를 수행하지 않는다.
- 같은 방향의 카드 쌍이 이미 연결돼 있으면 기존 연결을 반환하고 관계를 조용히 덮어쓰지 않는다. 이번 관계의 방향은 원본 카드 → 선택 카드다.
- 같은 카드 노드가 덱에 여러 개 있으면 order, id 순으로 첫 노드를 재사용한다. 새 노드는 기존 배치를 유지하며 하단에 추가한다.
- 추가 저장은 덱 행 잠금과 트랜잭션으로 처리한다. 기존 전체 그래프 저장에도 동일 잠금과 버전 검사를 적용해 오래된 편집 화면이 새 연결을 지우지 않도록 한다. 버전 충돌 시 409를 반환하고 프론트는 로컬 편집을 유지한 채 새로 불러오도록 안내한다. 기존 호출자를 함께 확인한다.

## 프론트 책임과 오류 처리

- entities/card: 반응·관련 카드 API와 쿼리, 이력 표시.
- features/card: 반응 입력과 선택적 연결 흐름.
- entities/deck: 연결 추가 API와 기존 덱 캐시 갱신.
- 카드 상세 페이지와 모달 모두 동일 흐름을 제공한다. 입력 중 닫기는 기존 모달 정책에 맞춰 미저장 입력을 보호한다.
- 반응과 연결은 각각 저장한다. 연결 실패로 저장된 반응을 되돌리지 않는다.
- 저장 중 중복 제출 방지, 실패 시 입력 유지와 재시도, 서버 멱등성 처리를 함께 적용한다.
- 기존 UI 컴포넌트와 디자인 토큰 사용. 키보드 선택, 명시적 라벨, 로딩·빈 상태를 제공한다.

## 검증 및 운영

- 백엔드: 다른 사용자 자산 접근 차단, 입력 검증, 동일 요청 재시도, 반응 삭제와 카드 삭제, 다른 책 후보 필터, 임베딩 누락, 중복 연결과 기존 노드 보존, 그래프 동시 수정 충돌을 기존 Jest로 검증한다.
- 프론트: 반응만 완료, 후보 선택/직접 선택 후 연결, 후보 없음, 저장 실패 후 재시도와 입력 유지, 모바일 상세/모달에서 완료 가능한지 검증한다. 기존 브라우저 검증 방식을 사용한다.
- 두 저장소 타입 검사·빌드와 변경 파일 lint를 실행한다. migration은 격리된 개발 DB에서 검증하고 운영 DB 적용은 별도 배포 단계로 둔다.
- 지표: 카드 상세 진입 대비 반응 저장, 반응 저장 대비 연결 완료, 경험한 사용자의 7일 내 재방문. 방문만 한 비교군과 관찰하되 선택 편향이 있으므로 재방문 상승을 곧바로 인과 효과로 해석하지 않는다.
- 측정 이벤트에는 식별자와 성공 여부만 사용하고 인용문·개인 메모는 넣지 않는다. 분석 수집 경로는 구현 시 기존 수단을 확인하며 새 분석 플랫폼 설치는 범위 밖이다.
- 사용자 로그와 검색 품질은 아직 검증하지 않았다. 이 설계는 출시 가능한 가설이며 경쟁 우위와 유지율 개선을 보장하지 않는다.

## 구현 순서

1. 반응 테이블·API·이력과 프론트 반응 저장을 완성한다.
2. 관련 후보·직접 선택과 멱등한 연결 저장을 구현한다.
3. 홈 진입과 카드 상세 흐름을 연결하고 실패·권한·동시 수정·모바일 검증을 마친다.

백엔드 쓰기는 환경 승인을 통해 수행했다. 반응은 별도 이력 테이블, 연결은 기존 덱 구조를 사용한다. 저장뿐 아니라 발행에도 expectedVersion 검증을 적용한다. 관련 카드의 실제 벡터 검색 품질과 운영 지표 수집은 로컬 안내 문서에 남긴 검증 한계를 따른다.
# 승인된 화면 분리 변경

상세보기에는 원문과 반응 이력을 표시한다. `지금의 생각 남기기`는 요약·반응·선택 메모만 보여주는 화면으로 진입한다. 저장 후 입력 폼을 완료 화면으로 교체하며 `마치기`를 기본 행동으로 둔다. 선택 행동인 `다른 카드와 연결하기`를 누르면 같은 화면에서 카드 선택 → 관계·덱 설정 → 연결 완료 순으로 전환한다. 모달을 중첩하지 않는다. API와 데이터 구조는 기존 설계를 유지한다.
